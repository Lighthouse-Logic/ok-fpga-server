# ADR-030: SSE Event Expansion

**Date:** 2026-08-23  
**Status:** Accepted — Implemented (Phase 39, commits `a593cf5`, `e8b52a2`; extended by [ADR-034](ADR-034-resource-model-consolidation.md) §2, §5, §12 & §14 with `resource_locked`, `resource_unlocked`, `resource_deleted.reason`, flat SSE payloads, and gRPC `WatchDeviceEvents` fan-out)  
**Phase:** [Phase 39 — Server-Side SSE Event Expansion](../../archive/roadmap-phases-39.md)  

---

## Context

The `DeviceEvent` enum in `ok-fpga-core::manager` currently broadcasts four
event types over the SSE endpoint (`GET /api/v1/events`):

| Variant | Trigger |
|---------|---------|
| `DeviceAdded` | FrontPanelManager detects USB device connection |
| `DeviceRemoved` | FrontPanelManager detects USB device disconnection |
| `DeviceProgrammed` | `POST /configure` or `/configure_from_server_path` |
| `ResourceChanged` | Resource acquired, released, locked, unlocked, or invalidated |

Meanwhile, the dashboard WebSocket (`broadcast_event` / `event_tx`) already
sends additional event types (`user_connected`, `user_disconnected`,
`resource_registered`, `resource_deleted`, `device_programmed`) through a
**separate** `tokio::sync::broadcast::Sender<String>` channel. These events
are visible only to the web dashboard — they are **not** available on the SSE
endpoint and therefore invisible to REST/gRPC API clients (including the
Python LabVIEW client's `EnvironmentMonitor`, ADR-C-009).

This creates an asymmetry: the dashboard has rich real-time visibility into
the server's full lifecycle, while API clients can only see device and resource
state changes.

## Decision

### 1. Add five new `DeviceEvent` variants

```rust
pub enum DeviceEvent {
    // Existing variants (unchanged):
    DeviceAdded { serial, product_name, interface, timestamp },
    DeviceRemoved { serial, timestamp },
    DeviceProgrammed { serial, bitfile, programmed_by, timestamp },
    ResourceChanged { resource_id, new_state, timestamp },

    // ── New variants (Phase 39) ──────────────────────────────

    /// A user session was created (first API call from this user).
    UserConnected {
        user_id: String,
        timestamp: DateTime<Utc>,
    },

    /// A user session ended.
    /// reason: "explicit" (user called disconnect), "timeout" (sweep expired)
    UserDisconnected {
        user_id: String,
        reason: String,
        timestamp: DateTime<Utc>,
    },

    /// A new resource definition was registered (POST /resources).
    ResourceCreated {
        resource_id: String,
        device_serial: String,
        name: String,
        timestamp: DateTime<Utc>,
    },

    /// A resource definition was deleted (DELETE /resources/{id}).
    ResourceDeleted {
        resource_id: String,
        timestamp: DateTime<Utc>,
    },

    /// The server is shutting down gracefully.
    ServerShutdown {
        reason: String,   // "signal" (SIGINT/SIGTERM)
        timestamp: DateTime<Utc>,
    },
}
```

### 2. HeartbeatTimeout folded into UserDisconnected

The sweep task detects heartbeat timeouts and removes the user session. Rather
than introducing a separate `HeartbeatTimeout` event, this is modeled as
`UserDisconnected { reason: "timeout" }`. The sweep already triggers
`ResourceChanged` events for any auto-released resources — the
`UserDisconnected` event adds the user identity context.

### 3. Broadcast from existing code paths

Each new event is broadcast at the same location where the dashboard's
`broadcast_event()` already sends its equivalent:

| Event | Broadcast Location |
|-------|-------------------|
| `UserConnected` | `heartbeat_middleware.rs` — when `touch()` creates a **new** session |
| `UserDisconnected` (explicit) | `server.rs` — disconnect handler |
| `UserDisconnected` (timeout) | `sweep.rs` — after removing expired user |
| `ResourceCreated` | `resources.rs` — `create_resource()` handler |
| `ResourceDeleted` | `resources.rs` — `delete_resource()` handler |
| `ServerShutdown` | `main.rs` — graceful shutdown signal handler |

### 4. `touch()` returns `bool` (Option A)

`UserSessionRegistry::touch()` is modified to return `bool`:
- `true` → new session was created (first call for this `user_id`)
- `false` → existing session was refreshed

This is a purely internal return value — nothing is sent over the network from
`touch()`. The heartbeat middleware uses this return value to decide whether
to broadcast a `UserConnected` event.

### 5. SSE handler match is exhaustive

The `events.rs` SSE handler's match expression gains five new arms:

```rust
DeviceEvent::UserConnected { .. } => "UserConnected",
DeviceEvent::UserDisconnected { .. } => "UserDisconnected",
DeviceEvent::ResourceCreated { .. } => "ResourceCreated",
DeviceEvent::ResourceDeleted { .. } => "ResourceDeleted",
DeviceEvent::ServerShutdown { .. } => "ServerShutdown",
```

Since `DeviceEvent` derives `Serialize`, the JSON payload is automatically
generated by `serde_json::to_string()` — no manual serialization needed.

### 6. Fix client-example SSE path

The Rust REST client example (`client-examples/rust-rest-client/src/lib.rs`)
references `/events/stream` but the actual server route is `/events`. This
is corrected as part of this phase.

### 7. OpenAPI specification update

The `DeviceEvent` schema in `openapi.yaml` is extended to include the five
new event types with their field definitions.

---

## Consequences

### Positive

- API clients get the **same real-time visibility** as the web dashboard.
- The Python LabVIEW client's `EnvironmentMonitor` (ADR-C-009) will
  automatically surface the new events — it parses the SSE `event:` field
  generically and converts to `snake_case`.
- `openapi.yaml` becomes the complete specification of all SSE events.
- The client-example SSE path bug is fixed.

### Negative

- The `DeviceEvent` enum grows from 4 to 9 variants. All `match` expressions
  on this enum must be updated (compiler enforces exhaustiveness).
- Slightly more traffic on the SSE stream (user connect/disconnect events
  are higher frequency than device events).
